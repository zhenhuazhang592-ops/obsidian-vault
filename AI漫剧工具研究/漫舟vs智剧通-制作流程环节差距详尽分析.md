# 漫舟 vs 智剧通(ZJT) · 制作流程环节差距详尽分析

> **分析日期**: 2026-03-25
> **分析目的**: 逐环节拆解两个系统的真实差距，明确漫舟的优化方向和优先级
> **说明**: 本分析基于漫舟全部28个Skill文件 + ZJT 7份研究报告，含两个系统核心代码/规范的逐行对照

---

## 分析维度说明

每个环节从以下5个维度评估：

| 维度 | 说明 |
|------|------|
| **机制差异** | 两个系统的具体实现方式有何不同 |
| **效果差距** | 这种差异在实际生产中会造成什么质量/效率差距 |
| **根因** | 为什么会有这个差距（是设计理念还是工程能力） |
| **优化成本** | 漫舟要弥补这个差距需要多少改动 |
| **优先级** | P0=立即/ P1=中期/ P2=长期 |

## 环节一：输入与项目初始化

### 1.1 初始化方式

| 能力项 | 漫舟 | ZJT | 效果差距 | 根因 | 优化成本 |
|--------|------|------|---------|------|---------|
| **用户输入形态** | 粘贴小说文本 | 空白画布 or 粘贴剧本 | 漫舟有短剧化改编（剃刀法则），ZJT无 | 设计理念不同：漫舟面向原始IP，ZJT面向制作 | P1 |
| **世界观管理** | 无world概念 | WorldModel + MySQL | ZJT支持多世界/多项目隔离，漫舟混在一起 | 漫舟无数据库层 | P1 |
| **全局配置强制化** | Step0强制选择（风格/画幅/时长）⭐ | 画布自由，无强制模板 | 漫舟配置更标准化，ZJT更灵活 | 漫舟的强制约束是优势 | — |
| **项目模板** | 16种风格预设（ShortDrama/WongKarwai等）⭐ | 无预设，手动设置 | 漫舟的presetId更结构化 | 漫舟更面向AI协作 | — |
| **会话状态** | 无会话概念，每次都是新上下文 | ChatSession内存存储 + SSE流 | ZJT有对话历史，漫舟每次都要重新加载上下文 | 漫舟依赖Agent上下文窗口 | P2 |
| **多集管理** | 目录分集（02-剧本/第01集.md） | episode_number字段 + DB查询 | 持平，ZJT的字段更灵活 | 漫舟文件命名方式简单够用 | — |

### 1.2 差距最大的问题

**漫舟的问题：每次新建项目都要从零开始配置**

```
ZJT:  选择world → 加载已有角色/场景/道具 → 新增资产
漫舟: 每次项目需要手动调用Step0-10，中途无法中断续做
```

**ZJT的优势：** 已有资产自动从数据库加载，新镜头直接引用已有char_01/loc_01。

**漫舟的现状：** CDP JSON定义好了，但每次生成还是要靠Agent"记着"去引用ID。

### 3.3 关键发现：一致性差距的真实根因

**漫舟一致性问题的根因不是DNA不够细，而是：**

```
漫舟的流程:  定义DNA手册 → 靠LLM在生成Prompt时引用DNA
              ↑
              问题：LLM可能引用错误/引用不完整/引用漂移

ZJT的流程:  定义角色 → 存入数据库 → 前端解析【【】】→ 自动查库 → 注入Prompt
              ↑
              关键：机器查库，没有LLM的主观错误
```

漫舟的DNA 6层锚点设计**比ZJT更细**，但执行层依赖LLM自觉性，ZJT的强制力来自数据库+前端解析。

**漫舟的真正优势**：DNA手册里有表情库、TanBin_V1/V2/V3变体、6层锚点——这些ZJT完全没有。漫舟需要在"执行层"借鉴ZJT，而不是在"设计层"落后。

## 环节四：剧本解析（LLM剧本→分镜）

### 4.1 剧本解析核心能力

| 能力项 | 漫舟 | ZJT | 效果差距 | 根因 | 优化成本 |
|--------|------|------|---------|------|---------|
| **解析引擎** | manzhou-shot-script.md（LLM Prompt） | parse_script_to_shots()（代码引擎，1100行）⭐ | ZJT的代码引擎更稳定，漫舟的Prompt引擎依赖LLM质量 | ZJT工程化，漫舟AI协作化 | P1 |
| **180度轴线** | manzhou-shot-script.md v5.0有规范（OTS双人对话格式）⭐ | **强制执行**，每角色独立镜头 ⭐⭐ | ZJT是系统强制，漫舟是规范提醒 | 两者都要落地到分镜，差距在执行层 | P0 |
| **多人对话拆分** | 规范中有OTS格式示例 | **强制拆分**，每角色独立镜头 ⭐ | 同上，ZJT更强制 | P0 |
| **强制中景对话** | 无 | **force_medium_shot参数**（对话禁止全景）⭐ | ZJT防止全景对话导致面部生成问题 | 漫舟暂无此规范 | P0 |
| **旁白模式** | 无 | **narration_as_dialogue参数** ⭐ | ZJT支持解说剧模式，漫舟无 | P1 |
| **时长重组算法** | 无 | **贪心分组算法**（同场景连续镜头合并）⭐ | ZJT节省视频生成成本（1组>2个独立镜头） | 漫舟暂无此算法 | P1 |
| **镜头时长建议** | 无 | 特写2-5s/全景5-10s有建议表 ⭐ | ZJT有精细时长建议，漫舟无 | P0 |
| **JSON健壮性** | 无 | **三层截断修复**（markdown清理→解析→截断修复）⭐⭐ | ZJT能自动修复LLM输出被截断的情况，漫舟遇到截断就失败 | 漫舟无健壮性机制 | P0 |
| **日志系统** | 无 | **9种日志文件**（每步操作完整记录）⭐ | ZJT可完整复盘每个分镜的生成过程，漫舟无 | P1 |
| **数据库关联** | 无 | location_db_id + props_db_id 自动注入Prompt ⭐ | ZJT从剧本直接关联资产库 | 漫舟无数据库层 | P1 |
| **场景嵌套** | 扁平 | parent_id+level（树形）⭐ | ZJT表达更丰富 | 同场景结构 | P1 |

### 4.2 剧本解析环节：最大差距

**差距1：JSON截断修复**

ZJT的实现：
```python
# 第三层：截断修复（如果JSON被截断）
except json.JSONDecodeError as e:
    if not cleaned_content.endswith('}'):
        last_bracket = cleaned_content.rfind(']')
        if last_bracket > 0:
            fixed_content = cleaned_content[:last_bracket+1] + '\n}'
            parsed_data = json.loads(fixed_content)
```

漫舟目前：LLM输出被截断 → 整个解析失败 → 需要手动修复

**差距2：多人对话拆分**

ZJT强制拆分：
```json
// 错误（ZJT禁止）：
{
  "dialogue": [
    {"character_id": "A", "text": "你好吗？"},
    {"character_id": "B", "text": "我很好，谢谢"}
  ]
}

// 正确（ZJT强制）：
镜头1: characters_present=["char_001"], dialogue=[{"character_id": "A", "text": "你好吗？"}]
镜头2: characters_present=["char_002"], dialogue=[{"character_id": "B", "text": "我很好，谢谢"}]
```

漫舟v5.0已有OTS双人对话格式，但**不是强制执行**，依赖LLM自觉。

| **单张参考图** | 单张分镜图Prompt ⭐ | 分镜节点独立生成 | 持平，ZJT更细粒度 | — |
| **参考图收集** | 手动拼接进Prompt | **节点连线→自动API收集** ⭐ | ZJT更自动化，漫舟手动 | ZJT有前端+API，漫舟无 | P1 |
| **角色标记解析** | 无自动解析 | **前端解析【【】】→ API查询参考图** ⭐ | ZJT自动完成一致性注入，漫舟靠LLM引用 | ZJT有前端自动化 | P1 |
| **相机描述** | Prompt手动写 | **yaw/dolly/pitch → 中文Prompt自动转换** ⭐ | ZJT更标准化，漫舟靠人工写相机描述 | P1 |

| **宫格处理** | Prompt中描述 | **宫格拆分+合并算法** ⭐ | ZJT有算法实现，漫舟靠文字描述 | P2 |

### 5.2 分镜图环节：最大差距

**核心差距：ZJT有前端自动化，漫舟全靠LLM手动**

ZJT的前端节点编辑器流程：
```
用户创建分镜节点
    → 输入imagePrompt文本
    → 前端解析【【谭斌】】→ 调用/api/characters?keyword=谭斌
    → 获取reference_image_url
    → 自动注入Prompt（buildShotFramePrompt）
    → 调用生图API
    → 返回thumbnail更新节点
```

漫舟的流程：
```
用户在manzhou-shot-script.md中写imagePrompt
    → 手动拼接：[ID: TanBin_V1], --cref TanBin_Ref_A_F.png
    → 依赖LLM自觉引用正确参考图
    → 无自动校验，无自动注入
```

漫舟九宫格分镜图Prompt是**差异化优势**（ZJT无），应保留并强化。

## 核心结论

### 漫舟真正的优势（在全行业中）

| 优势 | 说明 | 可持续性 |
|------|------|---------|
| **Lip-sync唇形同步** | 独立标注，ZJT完全无 | 🔥 长期差异化 |
| **Audio Layer音效层** | BGM+SFX注入VideoPrompt，ZJT无 | 🔥 长期差异化 |
| **进化飞轮** | P0+P1+P2三系统闭环，ZJT完全无 | 🔥 长期差异化 |
| **九宫格分镜图** | 3×3故事板，ZJT无 | ⚠️ 需自动化 |
| **DNA 6层锚点** | 比ZJT的appearance层更精细 | ⚠️ 需自动化 |
| **短剧化改编规范** | 剃刀法则/≤15字/45秒爽点，ZJT无 | ✅ 稳定优势 |
| **效果评分公式** | w1=完播率0.4等，ZJT无 | ⚠️ 需落地数据 |

### 漫舟最需要补齐的（直接影响生产质量）

| 短板 | 影响 | 紧迫度 |
|------|------|-------|
| **【【】】标记+自动查库** | 角色一致性依赖LLM自觉，规模生产必崩 | 🔴 最高 |
| **JSON截断修复** | LLM输出被截断就失败，无自动恢复 | 🔴 最高 |
| **严禁外貌进分镜** | 角色外观由--cref控制，不应混在Prompt里 | 🔴 最高 |
| **TTS API集成** | 音频环节全靠手动，无法自动化 | 🟡 中 |
| **剪映导出代码** | 规范再完善，不实现也无法导出 | 🟡 中 |

### 两者真正的差距本质

```
漫舟 = AI协作工具（Design层很强，Execution层靠LLM自觉）
ZJT = 制作执行平台（Execution层很强，Design层靠人工）

漫舟需要的不是学ZJT的全部，而是：
在Execution层（一致性/校验/导出）引入ZJT的强制机制，
同时保留Design层的差异化优势（Lip-sync/Audio Layer/进化飞轮）
```
